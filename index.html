Mindset — Você cria, a IA executa
A IA não tem visão, contexto nem responsabilidade pelo seu projeto. Você sim. Trate a IA como um estagiário talentoso que precisa de direção clara.

"A IA não cria sozinha. Nós criamos — a IA é a nossa extensão."

— fundamento deste manual
🧠
Você é o arquiteto
Toda decisão de estrutura, tecnologia e fluxo passa pela sua cabeça primeiro. A IA executa o que você direcionou.
🎓
A IA é o estagiário
Rápido, útil, cheio de conhecimento — mas sem julgamento próprio. Precisa de instruções claras e revisão constante.
🔍
Conheça seus pontos fracos
Se você é fraco em segurança, encontre a IA mais apropriada para isso. Não existe IA perfeita, mas existem as mais adequadas pra cada coisa.
🔄
Itere com consciência
Cada output da IA precisa ser avaliado por você. Nunca cole código sem ler. Nunca aceite uma resposta sem questionar.
Idea Como usar a IA a seu favor
📋
Geração de listas completas: não sabe todos os bancos de dados que existem? Peça pra IA gerar uma lista extensa e depois você avalia o que faz sentido pro seu projeto.
⚖️
Avaliação comparativa: use a IA pra comparar opções técnicas com base no contexto do seu projeto (latência, custo, escala, tipo de dado).
🔎
Antecipar problemas: pergunte à IA "quais são os possíveis pontos de falha nessa arquitetura?" antes de sair codando.
🧪
Geração de testes: a IA é excelente pra criar casos de teste, cenários de erro e edge cases que você talvez não pensaria sozinho.

Arquitetura — O mapa antes da viagem
Antes de escrever uma linha de código, desenhe seu projeto. Literalmente. Com cores, setas e formas. Seu cérebro aprende melhor quando vê.
por que desenhar?
Quando você era criança, aprendia desenhando. Seu cérebro ainda funciona assim. Um mapa mental colorido ativa conexões que texto puro não ativa. Pegue papel, caneta colorida e desenhe seu projeto. Cada cor representa uma camada: azul = banco de dados, verde = backend, amarelo = frontend...
como construir sua arquitetura
1. Comece pelo centro: qual é o núcleo do seu projeto?
2. Expanda por camadas: dados → lógica → interface → infraestrutura
3. Use cores diferentes pra cada camada (como na legenda acima)
4. Conecte tudo com setas mostrando fluxo de dados
5. Já nesse estágio, marque onde podem surgir gargalos ou falhas
Perguntas pra fazer à IA
• "Quais arquiteturas existem pra apps de [X]?"
• "Quais são os trade-offs entre monolito e microsserviços pro meu caso?"
• "O que pode crashar nessa estrutura?"
Antecipe os crashes
• Qual camada falha primeiro sob carga?
• O que acontece se o banco cair?
• Tem ponto único de falha (SPOF)?
• O que acontece com dados em trânsito?
mapa mental cores por camada fluxo de dados antecipar falhas
2
Banco de Dados — A fundação
A escolha do banco de dados impacta tudo: performance, custo, escalabilidade. Use a IA pra expandir seu leque de opções e depois decida com critério.
método: use a ia pra aprender mais
Não sabe todos os bancos que existem? Peça pra IA listar todos os tipos de banco de dados com casos de uso, prós e contras. Depois filtre pela sua necessidade real. Exemplo: o YouTube usa bancos específicos por causa de latência e volume de vídeos — o contexto muda tudo.
📊
Relacional (SQL)
PostgreSQL, MySQL. Ideal para dados estruturados, transações complexas, relacionamentos claros. Alta consistência.
🗃️
Documento (NoSQL)
MongoDB, Firestore. Flexível pra dados variáveis, ótimo pra escalar horizontalmente. Schema dinâmico.
⚡
Cache / In-Memory
Redis, Memcached. Ultra-rápido pra dados temporários, sessões, filas, pub/sub. Não persiste por padrão.
🔗
Grafo
Neo4j. Perfeito pra relacionamentos complexos como redes sociais, recomendações, grafos de conhecimento.
📈
Séries Temporais
InfluxDB, TimescaleDB. Otimizado pra métricas, IoT, logs com timestamp. Alta ingestão de dados contínuos.
🔍
Busca Textual
Elasticsearch, Typesense. Indexação full-text, busca semântica, filtros complexos. Complementa o banco principal.
Focus Critérios de escolha
  • Qual é o tipo dos meus dados? (estruturado, semi, não estruturado)
  • Qual o volume esperado de dados? (KB, GB, TB, PB)
  • Preciso de transações ACID ou eventualidade é aceitável?
  • Quais são os padrões de leitura vs escrita?
  • Preciso de busca full-text, geo, ou grafos?
  • Qual o custo de hosting (cloud vs self-hosted)?
  • Há necessidade de replicação ou sharding?
escolha criteriosa custo-benefício escala consistência

Backend — O motor
Construa o backend antes do frontend. Sem API funcionando, não há interface que funcione. Respeite essa ordem.
DADOS
BACKEND ← você está aqui
FRONTEND
a regra das etapas
Não faz sentido construir um frontend lindo pra uma API que não existe. Backend primeiro, sempre. Isso não é dogma — é lógica: você não pode testar uma interface sem dados reais fluindo.
🔌
Design da API
REST ou GraphQL? Defina endpoints, contratos de request/response e versionamento antes de implementar.
✅
Validação de dados
Todo input vindo do cliente é suspeito. Valide tipo, tamanho, formato, range. Use schemas (Zod, Pydantic, etc.).
🔐
Autenticação
JWT, OAuth2, sessões. Implemente autenticação antes de qualquer rota protegida. Nunca deixe pra depois.
📝
Logging & Observability
Você precisa saber o que está acontecendo em produção. Logs estruturados, traces e métricas desde o início.
🧪
Testes unitários
Use a IA pra gerar suites de teste. Peça especificamente por edge cases e cenários de falha.
⚡
Rate limiting
Limite de requisições por IP/usuário. Evita abuso, reduz custo e protege sua infra desde o começo.
🤖
Peça à IA: "Liste todos os pontos de falha possíveis nessa API REST que recebe dados de usuário e persiste no banco." A IA vai gerar uma lista que você usará como checklist de hardening.
API primeiro validação testes logging
4
Frontend — A vitrine
Só comece o frontend quando o backend estiver funcional. Interface sem API é teatro. Com API funcionando, você constrói com dados reais.
DADOS
BACKEND
FRONTEND ← você está aqui
🗂️
Componentização
Pense em componentes reutilizáveis antes de sair codando telas. Isso reduz duplicação e facilita manutenção.
📱
Mobile-first
Design e código pensados primeiro pra mobile. Escalar pra desktop é mais fácil do que o contrário.
🌐
Estado global
Onde vai viver o estado da aplicação? Context, Zustand, Redux, Pinia — escolha antes de começar a escalar.
⚡
Performance
Lazy loading, code splitting, cache de requisições. O frontend é o que o usuário sente — otimize com intenção.
♿
Acessibilidade
Semântica HTML, contraste, navegação por teclado. Acessibilidade não é opcional — impacta SEO e usuários reais.
🧪
Testes de UI
Cypress, Playwright. Teste fluxos críticos do usuário. Peça à IA pra gerar scripts de teste dos principais fluxos.
🎨
IA no frontend: use pra gerar componentes de base, mas sempre revise o código. A IA não sabe o contexto do seu sistema de design, suas regras de negócio nem os padrões do time.
componentes dados reais performance acessibilidade

Deploy — Da sua máquina pro mundo
Antes de jogar na nuvem, teste localmente. Antes de ir pra produção, teste em staging. Nunca pule etapas no deploy.

→
staging
→
produção
→
monitoramento
regra de ouro do deploy
Sempre teste manualmente antes de automação. Pipelines CI/CD são excelentes, mas você precisa entender o que está acontecendo antes de automatizar. Se algo quebra no CI e você nunca fez manualmente, fica perdido.
💰
Custo-benefício
Sempre avalie: AWS, GCP, Azure, Railway, Fly.io, Vercel. O mais caro nem sempre é o melhor pro seu caso. Calcule o custo projetado.
🔁
CI/CD
Automatize apenas depois de entender o processo manual. GitHub Actions, GitLab CI, Bitbucket Pipelines.
🐳
Containerização
Docker garante que "funciona na minha máquina" = funciona em qualquer lugar. Aprenda o básico antes de Kubernetes.
📊
Monitoramento
Uptime, erros, latência, uso de memória. Configure alertas antes de precisar deles. Não descubra a queda por usuário.
🔄
Rollback
Antes de fazer deploy, certifique que sabe como voltar. Blue-green deploy, feature flags, ou simplesmente git revert.
🌍
CDN & Edge
Assets estáticos perto do usuário. Cloudflare, AWS CloudFront. Reduz latência e custo de bandwidth.
🧮
Peça à IA: "Estime o custo mensal de rodar [descreva seu projeto] na AWS vs Railway vs Fly.io com [X] usuários simultâneos e [Y] GB de dados." Use como ponto de partida — não como verdade absoluta.
manual primeiro staging custo rollback
6
Segurança — O que você não vê te machuca
Segurança não é uma feature que você adiciona no final. É uma mentalidade que permeia todas as etapas.
saiba seus pontos fracos
Se você não manja de segurança, use a IA como seu especialista temporário. Peça revisão de código com foco em vulnerabilidades. Peça lista de vetores de ataque. Peça modelagem de ameaças. Mas lembre: a IA pode errar — use como camada extra, não como única verificação.
💉
Injeção (SQL, XSS)
Parameterized queries sempre. Sanitize inputs. Valide no servidor, não só no cliente.
🔑
Autenticação
Senhas com hash (bcrypt/Argon2). MFA quando possível. Tokens com expiração curta. Revogação de sessão.
🛡️
Autorização
RBAC, ABAC. Verifique permissão em cada endpoint, não só no login. Princípio do mínimo privilégio.
🔒
HTTPS / TLS
Sem exceções. Let's Encrypt se precisar de gratuito. HSTS habilitado. Certificados com renovação automática.
🚫
Rate Limiting
Limite tentativas de login. Limite criação de conta por IP. Protege contra brute force e scraping.
📦
Dependências
npm audit, Snyk, Dependabot. Suas dependências têm mais vulnerabilidades que seu código. Atualize regularmente.
🕵️
Prompt útil de segurança: "Faça um threat modeling desse endpoint [cole o código]. Liste todas as formas possíveis de abuso, bypass de autenticação, injeção e vazamento de dados. Priorize por criticidade."

7
Erros, Recomeços & Aprendizado
Errar faz parte do processo. Recomeçar não é fracasso. Às vezes, a decisão mais inteligente é jogar fora e começar com mais clareza.

"Às vezes compensa mais começar com assertividade do que corrigir inúmeros erros acumulados."

— filosofia deste manual
≠
Recomeçar ≠ Fracasso
✓
Errar = Aprender
∞
Iterar > Perfeccionar
🧹
Quando recomeçar
Se mais de 40% do código seria refatorado, recomeçar estruturalmente pode ser mais rápido. Não se prenda ao sunk cost.
📚
Documente os erros
Mantenha um doc de "o que não funcionou e por quê". Isso vira seu guia pessoal pra não repetir os mesmos erros.
🔬
Post-mortem
Quando algo crashar em produção, faça um post-mortem honesto: o que aconteceu, por que, o que muda. Sem apontar culpados.
🎯
MVP com intenção
Comece pelo menor produto que valida a hipótese principal. Menos é mais quando se está aprendendo o domínio.
Check Checklist antes de cada etapa
  • Entendi o que estou construindo e por quê?
  • Já testei manualmente o que veio antes?
  • Quais são os cenários de falha desta etapa?
  • A IA que estou usando é a mais adequada pra este problema?
  • Estou revisando o que a IA gerou ou apenas colando?
  • Tenho como reverter se der errado?
  • O custo desta decisão é proporcional ao benefício?
  • Estou respeitando a sequência de etapas?
